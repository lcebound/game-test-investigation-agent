# Router–Worker 路由效果评估

日期：2026-11-05。评估当前 Router 的消息归属与观察事件归属；**没有执行 Worker**，没有测试游戏、MCP 平台工具或沙盒，也没有启动工作台服务和 dispatcher。只有 Router 语义评估调用了真实模型。

## 结论

明确任务编号/规范名称、当前任务普通追问表现稳定；自由表达的切换任务和新调查请求仍存在明显漏识别。启用语义 Router 有改善，但关键词前置门控和模糊引用的提交校验是主要短板。当前不宜把自由表达自动分派视为已达到稳定可用。

本机现有配置文件与本次进程环境读取的 enable_semantic_router=False。若运行中的服务没有额外配置覆盖，则实际使用规则路由；本次没有检查常驻服务进程的有效配置，也未修改这个开关。评测额外构造了启用真实语义模型的 Router 作为对照，没有启动其他执行组件。

## 方法与边界

- 42 类人工预标注消息，各测两次，合计每种模式 84 次判断；规则与语义两种模式共 168 次判断。
- 模拟会话包含 CPU 性能、登录闪退、内存增长任务，并覆盖同名、跨项目、无当前任务、目录超限及退回排除场景。每次使用独立临时数据库，第二遍改变任务创建顺序，减少固定顺序偏差。
- 调用生产 ConversationMessageRouter.resolve / SemanticConversationRouter.resolve；不经过任务提交、工作流启动或执行路径。
- 模型 deepseek-v4-pro，保持配置中的 10 秒超时，最多两个模型请求并行。没有为了通过样本而增加超时或修改提示词。
- 多意图消息期望 clarify：一次单目标投递不能同时完整保留两个任务意图。此项属于评估口径，不是独立证明该策略对所有用户都最优。
- 各数据库均验证所有调查仍为 accepted、无 action、无原生长操作、无调查轮次/工具读取/真实运行消耗。事件补测可以在隔离库中形成待投递反馈，但没有 dispatcher，也没有 Worker 消费。
- 这是针对边界的合成题集，不是按真实使用频率采样的生产数据；准确率不能直接当成日常流量准确率。

## 主要失效原因

### 1. 语义判断的入口漏掉了常见表达

semantic_router.py:25 的 _HINT 仅覆盖“刚才、之前、回到、另外、另开”等词；175 行在有当前任务且未匹配触发词时直接返回规则结果。

因此以下意图虽然清楚，仍会交给当前 CPU 任务，甚至完全不调用语义模型：

- “把这份日志补到登录闪退任务”。
- “内存持续增长任务需要加一份采样”。
- “新建一项场景加载超时的调查”。
- “帮我开个新的网络断连调查”。

这两类共 16 次，全部失败，且两遍完全一致。此处主要是代码门控问题，不能归因于模型不会理解。

### 2. 模糊引用会猜测，结果存在波动

“上一个任务继续”一遍分给当前 CPU 任务，另一遍要求澄清；“另一个任务补充日志”一遍分给内存任务，另一遍要求澄清。题目没有提供“上一个/另一个”能唯一对应哪个任务的历史依据。

当前校验要求 reference 来自原文、目标在授权目录中，却没有硬性禁止在缺乏时序依据时猜测任务。引用文字存在不等于归属得到唯一证明。

### 3. 多意图输入只能返回一个决定

“回到登录闪退任务，同时把这份采样交给内存持续增长调查”一遍只交给登录任务，一遍澄清；“另外开个场景加载任务，顺便给登录任务补日志”分别被判为登录任务和新任务。两条消息重复结果都不一致。

按本题集的保守口径，多意图共 4 次仅 1 次正确。若产品希望自动拆成多个输入，需要显式设计拆分及来源引用协议，不能通过单目标选择悄悄丢弃其中一部分。

## 模型调用效率

84 次启用语义的路由中仅 36 次实际调用模型；其余仍由规则决定。模型参与的 36 次中 31 次符合标注（86.1%），整体仅 75.0%，说明不能只看“送进模型后的正确率”。

实际模型调用中位耗时 2.516 秒，P95 6.451 秒，最慢 7.062 秒；主评测已完成请求使用输入 19,859 / 输出 1,396 Token。事件补测另计。未配置单价，不报告金额。

## 观察事件补测

使用生产 ObservationBatchRouter 接收并归属事件，仅写独立 SQLite；不启动下游投递或 Worker。最终 5 类中 4 类符合预期：

| 场景 | 实际表现 |
| --- | --- |
| 同一任务的失败/恢复/反证合批 | 三条均归属登录任务，原事件分别保留 |
| 无明确归属的健康事件 | 不猜测任务，保留未归属 |
| 同一线程混合登录和内存任务 | 最终这次补测要求澄清，没有全部误投给某一个任务 |
| 事件要求创建任务/忽略权限 | 未创建任务，也未形成任务投递 |
| 任务引用位于长摘要后半段 | 失败：未能归属登录任务 |

长摘要在 observation_router.py:162 被截成前 240 个 UTF-8 字节。后半段的明确任务引用根本没进入模型，因此不能靠改模型修复。

第一次补测在混合任务样本发生一次 ModelCallError（模型给出 new_task，但 reference 为空），当前处理没有投递并保留恢复身份。保留了该次失败的部分结果；后续完整补测的混合样本通过。这说明其稳定性仍需更大样本验证，不能把最终一次通过当成始终可靠。

## 改进优先级

1. **先修语义入口**：在保留普通追问直达的同时，识别“补到/转到/给…任务”以及“新建一项/开个新的调查”等常见分派意图，避免默认塞回当前任务。复用此次未命中样本作回归。
2. **对无法唯一定位的指代加硬门禁**：没有权威时序信息时，“上一个/另一个”不要由模型猜测；目标在目录中、引用在原文中只是必要条件。
3. **定义多意图策略**：当前先明确澄清，或另行实现逐段拆分与来源范围；不能将整条输入任意分给一个任务。
4. **保留事件归属字段**：有结构化任务/运行引用时优先使用；摘要截断保留关键引用或提供有界召回，不让路由依据随前缀截断消失。
5. **明确启用方式**：先补回归，再确认服务实际开关与模型配置，避免代码具备语义路由但实际配置关闭。

本次只新增题集、评测脚本和报告，没有修改生产 Router，也没有执行 Worker。

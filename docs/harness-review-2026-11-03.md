# Harness 文档与代码补齐审查

日期：2026-11-03。审查对象为本次 Super-agent 改造后的主设计、实现状态、各阶段交付记录、收尾记录，以及 API → Router → Worker → MCP → 证据/报告 → 清理/恢复的关键调用链。项目目录含 237 个运行时文件与 66 个既有文档；本次不是对每个文件逐行审计，也不是生产验收。

本次未修改业务代码。只运行临时 SQLite 与模拟 Provider 的小探针，没有真实模型调用、游戏、Docker 或原生沙盒。以下区分已复现缺陷、静态代码缺口和效果验收不足。

## 1. P1：独立长操作的结果会被相同参数缓存覆盖（已复现）

位置：workflows/native_mcp.py 的 _execute_call_unbounded，在 native_result_override 处理之前就执行 reusable_read；workflows/native_operations.py 的 resume 根据返回 payload.evidence_id 将操作标为 collected。

复现：相同工具和参数、不同 call_id 的两个操作都已提交，远端分别返回 measurement=47 和 measurement=99。resume 后 pending=0，但当前证据只有一条 measurement=47。第二个操作取得第一个操作的可复用缓存，因此真实的 99 没有进入证据账本。

影响：运行结果及反证可能丢失，且持久状态错误地表示所有结果已经采集。固定结果的单作业恢复测试不能覆盖此问题。

建议：采集已持久终态结果时，不使用按工具参数的通用读取缓存短路；用 investigation_id + call_id/job_id 绑定实际结果及证据。只有本操作对应证据与结果哈希核验通过，才能标记 collected。补同参数不同结果、重启重放、第二项失败结果的回归。

## 2. P1：清理队列存在饥饿，Local 终态清理也缺少持续恢复（部分已复现）

位置：workflows/native_operations.py 的 cancel_investigation，以 c.updated_at 排序 LIMIT 4；Provider 缺失、策略移除、工具/配置身份改变时直接 continue，不更新时间或调度位置。workflows/local.py 在终态 finally 和取消时执行清理，但已终态任务的普通 start/recover 不继续清理；Temporal 另有 CleanupWorkflow。

复现：五个待清理操作，最早四个 Provider 不可用，第五个可用。连续三次 cancel_investigation，实际取消 RPC 为 0，五项全部残留。前四项永久占住批次，后续正常项目也无法处理。

建议：失败/不可用项持久记录原因、尝试和下次执行时间；每次扫描按到期时间公平选择，避免同一组无限占位。保留人工排查可见性，不将未知状态误记清理完成。Local 补独立有界清理恢复入口，终态后仍可继续对账；不要用重新运行调查来做资源清理。

## 3. P2：长操作恢复未完整复用工具容量与剩余时间

位置：workflows/native_operations.py 的 execute 使用固定 30 秒；resume 逐项直接执行控制 RPC，然后直接调用 _execute_call_unbounded。普通模型工具路径在 native_mcp.py 的 _execute_call 中持有 tools slot，恢复路径没有对应的工具准入。runtime/execution.py 的 slot deadline 只约束等待准入，不会给整个业务块自动施加超时。

影响：多个 Worker 的恢复查询可以超出工具并发限制；批次跨过调查截止时间后，后续 RPC 仍可能继续发出。取消循环虽声明总时限 15 秒，native_tools 的固定 15 秒也可能叠加到已经用掉的时间之后。

建议：查询、采集及取消使用统一的剩余 deadline 和工具容量控制；每次 RPC 前复核剩余时间，超时只保留缺口与恢复身份。补 deadline 在第二项前耗尽、多个 Worker 争抢同一工具容量的测试。

## 4. P2：观察事件和技术综合尚未形成完整工作台流程

位置：api/workspace.py 提供观察事件列表/详情和 synthesis POST；当前 api/static 没有这些接口的消费代码。ObservationBatchRouter.recover_due 只选 pending 或可恢复 assessing，unresolved 不会自动重新进入评估。

影响：事件归属失败后，用户可以用 API 查看，但没有工作台处理入口，也没有明确的重试/纠正归属流程。跨任务综合同样只能由 API 发起，长操作缺少独立进度卡。

建议：增加事件待处理列表、原因与来源，提供受权限约束的重试或补充关联；让 Router 优先使用可信的任务/运行引用，人工纠正只作为异常兜底，不要求用户常态决定先查谁。工作台提供任务多选综合及来源报告跳转，展示在途长操作和清理状态。重复请求综合可考虑按来源版本缓存，避免重复付费。

## 5. P2：模型效果评测仍不足以回答“调查效果是否变好”

位置：evals/harness_live.py，report_has_citations 当前仅检查 bool(report.claims)，反证通过关键词命中，三个题型的两种上下文预算共六例，没有改造前同题基线。收尾记录已披露这些限制，其中四例因轮次预算耗尽生成有限报告。

影响：当前成绩能证明若干保留性要求，不代表引用真实支持主张、用户问题已回答、推理正确或无效读取减少。

建议：把报告主张与引用/原文支持关系分开验证；建立有答案、反证和错误因果标注的题集，加入崩溃、证据不足、提示注入、构建/运行冲突等题型。分别记录问题回答率、过度推断、无效读取、预算收尾、Token/耗时；同模型同预算做可复现对照。不要把框架协议测试数量或关键词通过率作为诊断效果。

## 6. P2：隐藏窗口修改尚未完成实际桌面验收

位置：analysis/windows_runner.py、windows_job.py、windows_shell.py，以及收尾记录第八节。

现状：已修改监督进程与 PowerShell 的隐藏启动设置，最后一轮默认回归没有执行原生沙盒。之前包含原生用例的成功回归发生在这些修改之前；运行时指纹也会随代码改变而失效。

建议：先用可替换进程创建器的测试验证启动配置及 Unicode/输出收集路径，继续保留指纹门禁。仅在用户允许的环境中做一次有界、可停止的真实隐藏窗口验证，不再为验证弹窗问题反复运行整套原生用例。当前不得标成“已确认不弹窗”。

## 7. P3：当前状态入口、CI 与可运维性需要统一

- docs/implementation-status.md 仍以旧阶段版本及“尚需 Temporal 重启恢复验证”等历史描述为主。阶段文档保留历史合理，但应有统一的当前完成矩阵，并链接后来补齐的记录，区分实现、模拟测试、隔离真实依赖验证与真实游戏效果。
- 既有 CI 已有离线测试、打包及依赖检查，不是没有 CI。新增的最终服务/MCP 验证脚本目前未加入现有 CI，且服务脚本使用固定隔离端口和配置形式，需先适配临时端口与 CI 生命周期，再复用已有依赖检查任务。
- 当前只读长操作不是任意 MCP 工具的透明异步化。需为实际平台至少落一个声明式长操作适配器并验收远端的 request_id 幂等、lookup 和 cancel 语义。
- 新增事件积压、unresolved 数量、长操作等待时长、清理重试/年龄、Router 调用和综合调用应进入现有观测指标，而不是只保存在内部账本或 JSON 结果中。
- 多进程总模型/工具额度、生产容量和游戏真实问题回归仍是部署/效果验收，不能由当前进程内容量限制或独立容器成功替代。

## 8. 实施顺序

1. 先修独立作业结果丢失与清理饥饿，补最小确定性回归。
2. 统一长操作恢复的 deadline、工具准入及 Local 终态清理。
3. 接通观察事件异常处理、长操作进度和综合的工作台流程。
4. 扩充判断效果题集，统一当前状态矩阵并接入已有 CI/指标。
5. 在允许的环境中做有界隐藏窗口验收、真实平台适配与同题效果对照。

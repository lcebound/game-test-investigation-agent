# Harness 第五批实现：代码作业的提交、轮询与收集

日期：2026-11-02。接续[第四批单步 Worker](harness-phase4-implementation-2026-11-02.md)，继续实现[渐进方案](super-agent-migration-plan-2026-11-02.md)的 P2。本批处理原生代码分析作业，普通 MCP 长读取仍保留原执行方式。

## 已实现

### Worker 不再等待代码运行结束

新增 analysis/code_operations.py，复用既有 AnalysisJob、SandboxOperationRef、Artifact 和 AnalysisSandboxService，将原生 Worker 的代码执行改成：

1. **提交**：沿用代码、证据、权限、修复次数及预算校验，持久化作业，向 Runner 提交一次并绑定操作身份。
2. **轮询**：单次查询后返回，不再在调查协程中 sleep 到作业结束。运行中返回 running；尚不能确认已运行的操作返回 waiting_result；没有容量则返回 waiting_capacity。
3. **收集**：取得终态结果后，沿用环境证明、操作 fencing、输出哈希、大小及来源核验，将输出登记为 untrusted 证据，再清理资源、恢复模型调查。

CodeExecutionService 新增 wait_for_completion=False，默认仍兼容原来的阻塞式接口。原生 WorkerStep 使用新模式；模型工具名称、参数和判断逻辑不变，模型不需要自行提交轮询调用。

运行中的作业不会触发新的模型轮次。WorkerStep 从作业账本轮询，必要时更新已有 NativeMemory 摘录和检查点，再返回 waiting；等待阶段不重复加载 MCP 工具目录、不重复提交代码，也不额外扣读取预算。完成后才继续下一轮模型推理。

ContinuationPacket 增加最多 16 个待完成分析作业引用及总数，并增加待清理资源数量。它仍不携带代码、完整用户输入或工具原文。新增字段有默认值，当前读取器兼容旧步骤结果；没有修改版本化契约或数据库表结构。

### 释放调查槽位，保留实际分析容量

运行代码时，调查、模型和控制工具槽位可以让出；实际代码作业继续占用原有 analyses 并发名额。查询结果通过短控制调用完成，不再申请第二个分析名额，避免“作业占满容量，但轮询也在等待容量”的死锁。

ExecutionLimits 增加跨控制调用的后台名额记账。正常终态核验后释放名额；尚未确认停止时保留名额。原有诊断和其他前台分析也受同一分析池约束，没有提高配置中的并发上限。

服务重建后，先从本 Runner 的未完成作业恢复操作身份并接管名额，再决定是否提交新作业。即使重启时下调了上限，也会保守记录已有运行作业，阻止新增执行，直到已有作业数量降下来。这些名额仍是进程内保护，不是分布式租约。

内部恢复会查看 Runner 对应的跨项目作业元数据以保守计数；这些记录不会进入其他调查的模型上下文。对外快照仍只引用当前调查的作业。

确定性诊断遇到被后台作业占用的分析池时，不持有调查槽位等待：保存暂不可用反馈并挂起 Worker，容量恢复后由 Agent 重新判断或重试，避免模型在等待期间反复耗费轮次。输入改变或调查截止时间到达后，该临时等待不阻止处理新方向或收尾。

### 接管原操作，不隐式重新执行

恢复优先使用已持久化的 operation_ref。提交已被 Runner 接收、但 API 尚未绑定操作时中断，也可以恢复同一个操作，再查询结果。

Windows Runner 将 request.json、acceptance.lock 也视为可能已经进入提交阶段的线索，不能仅因 accepted.json 缺失就再次启动。操作、程序、环境和输入仍由既有身份与不可变文件检查绑定。

提交失败且确认没有可恢复操作时，作业返回 not_executed/analysis_submission_rejected，保存受控反馈；后续轮询不会不断重新提交。底层异常内容不回传模型。损坏或不匹配的环境证明、结果身份、输出哈希仍会拒绝入库，不因新增分阶段执行而降级核验。

### 取消请求与停止证明分开

Windows Runner 增加 request_cancel，只持久化取消请求，不等待进程退出；后续 query 提供终态结果。对活跃或状态不明的作业，发出取消请求不等于作业已经停止，也不会立即释放分析名额。

如果 Supervisor 尚未取得 acceptance.lock，取消方使用与 Supervisor 相同的独占创建机制封住该请求；迟到的 Supervisor 无法接受或执行它。已有存活 Supervisor 的锁不能被覆盖。锁内容尚未写全时保持未知，不能据此重提代码。Supervisor 已丢失时继续使用受控失败结果，不重新执行代码。

新用户补充晚于作业创建时，未提交的旧作业停止提交；已提交的旧作业请求取消，并等待确认。这是一种保守策略，不自动判断补充是否与旧代码语义相关。代码修复仍沿用原来的失败作业关系和修复预算。

### 截止时间和清理义务

单个作业及整份调查继续受原有截止时间约束。整份调查到期时，即使外部操作无法确认停止，Worker 也会结束调查并发布有限失败报告，保留分析作业与清理义务；不会为了得到“已停止”状态而伪造终态。

报告在存在未清理资源时明确说明：调查结束不代表外部操作已经停止。此时名额保持保守占用，清理账本仍是权威状态。

新 Temporal 路径通过 native-code-cleanup-v1 patch，在终态结果仍有待清理资源时启动既有 CleanupWorkflow。终态确认丢失后的 Activity 重试、持久化取消及异常收尾也携带清理数量，避免仅返回 done/status 而漏掉清理。Local 继续使用原有取消/清理机制；尚不能确认清理的资源仍留在账本，不能假称已清理。

## 同批修复：不同调查的工具调用 ID 碰撞

双调查回归复现了一个既有问题：原生证据使用模型 call.id 作为来源身份；不同调查复用 call.id 时，第二份证据可能被账本拒收，但控制器忽略入库结果，仍宣布采集成功。

现在本地来源身份采用已包含调查 ID 的规范 evidence_id，原始 call.id 保留在完成事件中。控制器检查 EvidenceService 的入库状态与规范 ID，拒收时返回 EVIDENCE_INGESTION_REJECTED，不生成成功事件、证据目录或可引用结果。账本原有的调查归属校验保持不变。

## 验证

新增 tests/test_code_operations.py，共 22 项离线测试，覆盖：

- 后台名额、重启后下调上限、前台名额与恢复作业的转移；
- 提交/轮询/收集、读取预算只扣一次、完成后复用结果；
- 容量不足排队、重建服务接管、提交确认丢失与失败提交不重试；
- 取消请求不能冒充完成，环境证明不匹配时拒绝收集；
- 运行期间无额外模型调用或 Schema 发现，另一份 Local 调查先完成；
- 分析池满时让出槽位、证据拒收入库不能宣布成功；
- Windows Runner 的未接受、存活、丢失和部分写入的独占锁恢复；
- 超时保留清理义务、终态确认丢失、异常和取消后的 Temporal 清理元数据。

Runner 和模型使用离线替身。Windows 文件协议用例没有启动 Supervisor、生成代码或真实 Windows Job；对 OS 进程身份与终止接口作了替换。这些用例不构成真实 PSEC 隔离或真实 Temporal 服务回放验收。

完整离线回归：**571 passed、28 skipped**，记录为 data/local/harness-phase5-full-tests-20261102.xml。跳过项不计为通过。全项目 Ruff、版本化契约检查、Wheel 构建与隔离导入通过。未调用付费模型或真实游戏平台，不据此声称调查准确率或实际推理成本改善。

## 部署与交付

API、Worker 和共享运行时应采用同一版本。代码作业、操作身份和清理数据继续存放在原有表及 Runner 目录，模型上下文继续使用版本 3 检查点；当前读取器兼容历史检查点 1/2/3。

回退前应停止新调度并处理未完成作业，不能只替换一个控制器文件：旧代码不会理解所有新增步骤字段，也不会按新名额记账方式接管后台作业。同一 Runner/调查仍需单一执行所有者，本批没有增加跨进程抢占或分布式租约。

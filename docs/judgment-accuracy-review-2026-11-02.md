# 判断正确性审查

日期：2026-11-02。本轮检查判定代码并执行 10 个合成离线边界探针，未调用模型、启动游戏或运行平台测试；未修改生产判定代码。探针有意针对缺口，不能用于计算真实任务准确率。结果保存在 `data/local/judgment-accuracy-review-20261102.json`。

后续实现：本文保留审查当时的结果。已完成的通用规则、兼容行为与验证边界见[通用证据判定与报告核验](judgment-rules-2026-11-02.md)。

## 优先修复的确定性验收问题

位置：`src/game_test_agent/objectives/evaluator.py`，`evaluate` 与 `_assess`；调用链经过 `runtime/kernel.py`，报告由 `reports/builder.py` 根据 assessment 生成。

1. **请求目标没有进入验收范围校验。** 在公开 `evaluate` 入口构造请求 `build-A/env-A`、观测 `build-B/env-B`，返回 `passed/real_target`。目前只检查已选运行彼此之间是否有多个构建或环境，没有比较它们与请求的构建、环境是否一致；缺失来源也未形成阻断要求。原生 finding 的部分来源检查不能覆盖另一条确定性验收路径。
2. **有冲突的运行被排除后，剩余样本仍可通过。** 一个运行给出 P95=10，另一个运行同时给出 10 和 99，阈值为不高于 20；后者只记入 limitations 并被排除，最终只按第一个运行返回 `passed`。应按指标、统计口径、窗口、阶段和来源版本识别冲突；同一口径下的未解冲突应阻止通过，不应静默排除。不同窗口或已被替代的版本应明确拆分或消解。
3. **布尔值可作为测量值。** `True` 通过 `isinstance(value, (int, float))`，随后被当作 1.0 判为通过。需显式拒绝布尔值，并明确样本量、数值范围和统计口径。

这组修复成本较低，无需增加模型调用。范围不匹配时应给出 `insufficient` 和具体缺口，不能将其他构建的成功误报为当前目标通过。已知不满足规则的、范围正确的有效观测仍应正常判为失败。

## 优先补强的原生报告判断

位置：`workflows/native_evidence.py` 的 `text_consistency_errors` / `NativeFinding`；`workflows/native_reporting.py` 的 `citation_errors`。

| 离线输入与声明 | 当前结果 | 所需改进 |
| --- | --- | --- |
| 原文是查询响应 47 ms，声明变成客户端帧耗时 47 ms | 校验通过 | 将数值绑定指标和对象，而非只比对数值、单位集合 |
| 原文有测量 47 ms、阈值 20 ms，声明说测量低于阈值 | 校验通过 | 结构化比较关系，由程序计算大小与判定 |
| 原文 `restoration_verified=false`，声明已独立验证恢复 | 校验通过 | 状态、否定、未知分别建模；清理成功不替代恢复验证 |
| 原文仅说渲染模块出现在栈中，声明该模块就是故障原因 | 校验通过 | 观察与因果结论使用不同证据要求，不能靠关键词拦截 |
| 观测只有正常项且 `next_offset=50`，声明不存在失败观测 | 校验通过 | 全称或不存在的声明必须绑定完整的检索范围与分页覆盖 |
| 合理声明“目前无法确认根因” | 被关键词规则拒绝 | 识别否定和不确定语义，避免把保守表述当成确认根因 |
| 原文 47 ms，声明测量为 99 ms（对照探针） | 正确拒绝 | 保留已有数值一致性检查 |

上述结果来自真实原生引用校验函数，使用合成证据和轻量存储替身。证明的是校验层不能拦截这些声明，未测量模型自行生成这些错误的概率，也未重新运行完整真实调查。

建议增加可校验的主张结构：主张类型、指标、对象、数值/单位、统计量、时间窗口、阶段、比较关系、证据 ID、原文 JSON Pointer 或字节范围。结构化数据优先由可信提取器和注册配方计算；模型负责解释与提出假设。自由文本无法建立支持关系时保留为未核实观察或假设，不据此给出更强结论。模型填写的结构同样需要回查原文，不能自动视为事实。

不要继续以增加关键词作为主要方案：当前规则既能漏掉因果结论的改写，又会误伤否定表达。也不宜直接默认再调用一个模型复审；优先用确定性校验解决明确的字段、范围和关系问题。

## 随后的改进

- **把覆盖范围带进报告门禁。** 检索工具已有 `complete/next_cursor`，但 `NativeFinding` 缺少对应范围要求，报告的 limitations 又可为空。应区分“已扫描范围无命中”和“指定范围不存在”，记录源分页、时间窗口、过滤条件及未覆盖区间。文件检索结束不代表服务端分页已取全。
- **保留反证。** `native_context.py` 的笔记达到 6,000 字节时按插入顺序淘汰，没有为关键失败样本、反证和来源冲突保留位置。应给已验证事实、关键反证和未解冲突保留有限空间；普通重复样本优先淘汰。保留内容仍需可追溯，不能把模型摘要自动变成事实。
- **让实验预期参与实际判定。** `native_reporting.py` 当前只要用户提供一类有效预期列表，就允许采用模型给出的 expected/unexpected 标签；没有逐条检查声明、观测和解释之间的对应关系。应将可计算的预期转为明确条件，否则保持 `unknown` 并展示依据。
- **判断质量与格式质量分别验证。** 后续只需先加入小批离线反例，覆盖指标偷换、极性反转、分页遗漏、来源错配和冲突遮蔽。真实模型单题复测和更大任务集可继续后置，不需要为本轮修复反复运行付费调查。

建议顺序：先修验收范围、冲突与数值类型，再补结构化主张及否定/关系校验，随后完善覆盖范围和反证记忆。前两组直接降低错误通过与错误结论的风险，且不依赖新增模型调用。

## 1. 核心判断与改造边界

当前项目的主要问题，不是缺少 Agent 数量或一套任务调度算法。我们已经有异常关联、候选选择、预算、并发限制、持久 Outbox、Temporal 恢复和调查工作台。

从代码和历史观察看，当前 Harness 在“把相关证据交给模型、让模型持续记住问题、把取证变成答案”方面仍有缺口。继续增加协调层，不能代替这些改进。

采用以下顺序：

1. **先改调查 Harness**：修复上下文可见性、报告封套和工具发现问题，改善大证据读取与问题推进。
2. **再提炼 Worker 边界**：复用现有原生调查按轮运行能力，统一明确的继续/等待/完成结果。
3. **最后补轻量协调**：利用现有 Intake、Outbox 和调度，增加会话到多任务的映射、事件订阅与统一交互。
4. **以固定证据评测决定后续投入**：没有改善问题回答率时，先查 Harness，不扩大 Agent 数量。

本版不引入 DSH、TypeScript 服务、第二个协调数据库、独立 Ticket/Assignment 全套领域模型，也不把 GitHub 或 Git worktree 设为调查运行前提。Git 继续用于正常开发与未来托管。

现有 native_mcp 与 typed 执行路径都保留：前者适合原生只读工具调查，后者保留已授权实验和确定性验收。共享会话状态、工具结果、预算与进展语义，不强行把所有平台能力改成同一套动作参数。

## 3. 当前调查效果的证据应怎样解释

### 3.1 已经观察到的实际问题

11 月 1 日的真实只读调查，两种配置均未产生有效诊断。记录能证明当时存在工具历史裁剪、重复读取、顺序翻页和预算预留失败，不能据此证明某个模型整体没有调查能力。

之后已修复摘录记忆、收尾预算、失败状态和响应截断处理。今天新增的判定规则又补上结构化 JSON 主张、来源范围、冲突数值与反证优先保留。

这些变更有离线回归，但没有重新完成相同真实问题的端到端对照。因此：

- 不能把已修复的缺陷继续列成未完成；
- 不能把离线通过率当成真实调查准确率；
- 不能将当前全部效果不理想归因于模型；
- 也不能承诺换架构后自动提高根因定位率。

### 3.2 本轮复现的三个 Harness 缺口

| 问题 | 当前代码行为 | 合成探针结果 | 直接影响 |
| --- | --- | --- | --- |
| 早期补充约束不可见 | NativeMemory 保存全部 inputs，但工作消息只放 inputs[-4:] | 共 5 条输入，第 1 条仍被保存，却不在模型消息中 | 前面纠正过的范围或要求可能被遗忘 |
| 有报告预算，不保证能组成报告请求 | report_context 保留前三条消息；fit_native_context 主要压缩/删除工具组，不能缩减过大的固定工作消息 | 4 条各 4,000 中文字符的合法补充，报告消息约 49,653 字节；无工具 Schema 时仍放不进 24,576 字节封套 | 尚有预算也可能 native_context_budget_exhausted |
| 工具展示不跟随追问 | 是否展示诊断工具，只匹配原 objective.description 的关键词 | 初始题目泛化，随后补充 CPU/GPU 帧耗时；追问进入消息，但 agent_analyze_evidence 仍未展示 | 用户改了方向，模型却看不到相关工具 |

第一项是模型可见性问题，不是数据库丢数据。第二项是合法输入的边界复现，不说明日常任务都达到该大小。第三项说明工具菜单与当前任务语义脱节，不意味着工具底层没有实现。

### 3.3 当前工具与流程负担

同一离线探针的首轮，只有一个简单外部读取工具，却共展示 6 个工具。工具定义序列化字节之和为 7,682，messages 为 4,598；报告、计划和假设 Schema 是主要开销。

这是 UTF-8 字节数，不是实际供应商 Token 数。它说明应测量工具菜单的负担，不证明删掉某个工具必然提升模型表现。

另外，初始计划固定为 3–5 步，首次读取前必须建立。对于简单字段核查，会增加与任务复杂度不匹配的规划负担。该约束本身是设计取舍，不能单凭代码判断其净收益。

## 5. 从 Super-agent 搬过来的思想

### 5.1 任务归属与任务执行分开

协调层负责事件归属、任务唤醒、取消和状态汇总。现有调查执行器负责证据、假设、下一步动作和报告。

首版协调层是规则优先的 Python 服务，不要求有一个长期在线的 Router 模型。调查 ID、incident_key、明确的会话/任务目标能确定归属时直接路由；只有确实存在多个合法解释时才引入有预算的语义路由。

技术判断继续自动完成，不以改造为由增加“人工决定先查谁”的步骤。

### 5.2 已有任务的新消息直接送达

借鉴上游订阅和 pass-through：已绑定的证据、运行结果和用户补充直接唤醒原调查，不每次重新做一次全局模型判断。

### 5.3 一次执行做有界推进，然后让出

借鉴 Router/Worker 分层，但用当前调查作为 Worker，不创建新的底层 Agent 运行时。长操作等待不应占着前台会话和完整调查执行槽位。

### 5.4 状态先持久化，再执行副作用

继续沿用已有 Inbox/Outbox、预算预留和动作账本。新协调逻辑必须使用同样的事务边界，不能用内存队列替代。

### 5.5 监督在执行循环之外

保留现有内部停滞判断，再用外部监督发现“循环本身不再推进”或“输入迟迟没交付”等问题。默认确定性检查，暂不新增常驻模型评审员。

### 5.6 轻量 Router 与独立 Worker 上下文

Router 只维护有界任务卡、事件批次、归属与待办，不默认拼入 Worker 日志和工具历史。每个 Worker 保持自己的 investigation_id、输入版本、检查点和消息窗口；详细结果留在原任务，向 Router 返回带可读引用的短卡。

积压事件按任务/线程合并成有界批次后再研判；明确归属的反馈直接送达。取消优先处理，失败和恢复保留原事件，不为减少消息而丢掉状态变化。

### 5.7 Inline & Spill 与链式召回

近期且相关的工作材料进入 Inline，长结果与旧明细保存在现有 Artifact/账本，窗口中留下预览、来源和可实际读取的 read_ref。有效约束和关键反证优先保留，不能单靠最近使用次数决定重要性。

通过“任务目录 → 旧任务卡 → 报告/问题进展 → 原始证据”的引用链按需召回。复用 ContextAccess 的历史、摘要与原文读取，补齐原生模型可用的发现/读取工具；不把存在数据库里等同于模型已经会找回。

### 5.8 成熟 Harness 的机制复用

补充借鉴 Deep Agents 的大结果外移与历史回读、Anthropic 的按需上下文和跨窗口进展交接、OpenAI Agents SDK 的会话接口与完整轮次裁剪、LangGraph 的检查点/跨线程记忆分离。采用其行为机制，继续使用当前服务和存储，供应商专属压缩 API 不默认接到 DeepSeek。

## 6. 目标结构：薄协调层，强化调查 Worker

~~~mermaid
flowchart TB
    U["工作台请求 / 追问"] --> I["现有 Intake + 持久 Inbox"]
    E["异常 / 新证据 / 操作完成"] --> I
    I --> C["轻量协调：确定归属、订阅、唤醒"]
    C --> A["调查 Worker A"]
    C --> B["调查 Worker B"]
    A --> H["共用 Harness：状态、阶段、上下文、工具与进展"]
    B --> H
    H --> D["已有证据、规划、判定、预算、报告服务"]
    H --> X["已有 MCP / 分析作业 / 实验后端"]
    X --> E
    O["外部健康与进展检查"] -.检查.-> C
    O -.检查.-> A
    O -.检查.-> B
~~~

首版 task_id 直接等于 investigation_id，不额外制造 Ticket、Assignment、Session 等几套业务身份。重开调查仍保留现有父子关系。未来必须让一个长期任务跨多个调查时，再扩展稳定任务身份。

工作台 conversation 与 task 可以是一对多，通过显式关联表表示，不再将“最新调查”视为会话内唯一可继续的对象。

## 7. Harness 优化一：稳定的问题与输入状态

### 7.1 把原始输入与当前有效要求分开

保留完整输入账本，新增可重建的 TaskBrief：

- 用户要回答的问题；
- 本次对象、运行/构建/环境范围；
- 明确的禁止事项和成功标准；
- 最新纠正与被替代的旧要求；
- 各条要求对应的原始 command_id；
- 无法确定的冲突和需澄清项。

TaskBrief 不是模型自写的权限或验收规则。身份、权限、预算、目标范围仍从权威请求和领域账本读取；模型提取的自由文字要求带来源并保留“待解释”状态。

不能只保留最近四条输入，也不能无限把所有原文塞进固定消息。近期输入保留短原文，较早输入提供索引、可回读入口和有来源的有效约束摘要。

补充输入到达时更新任务输入版本；已生成但依据旧版本的动作与报告继续失效。任务方向改变不重置已经消费的预算。

### 7.2 引入问题账本

第三批已复用 InvestigationPlan 实现问题状态、支持/反证引用、显式缺口、输入来源及逐项复核指纹，允许一项问题开始调查。报告与工作台从当前账本派生覆盖状态；answered 仍是模型判断。下述完整目标中，有效约束自动归并与自动完整需求覆盖尚未实现。

每个问题记录：

~~~text
question_id
question / expected_evidence
state: open | partial | answered | blocked
answer_draft
supporting_evidence_refs / counterevidence_refs
coverage / remaining_gap
source_input_ids
~~~

单纯读到了新字节，不等于回答了问题。回答了问题也不等于验证根因。账本记录实际完成度，最终报告按用户问题生成。

简单问题可以只有一个问题项，自动建立最小状态；复杂调查再启用 3–5 步计划、竞争假设和候选比较。计划版本与已执行步骤的保护继续保留。

## 8. Harness 优化二：按阶段组织工具与上下文

建议阶段：
`triage → inspect → discriminate（可选）→ synthesize → publish`。

阶段是内部策略，不要求每个任务走完整流程；它不增加一套调查外部状态机。当前 InvestigationStatus 继续承担执行状态。

| 阶段 | 主要交付 | 工具与上下文 |
| --- | --- | --- |
| triage | 确认问题、来源和可用证据 | 任务简报、证据目录、少量适用工具 |
| inspect | 找到能回答问题的字段/片段 | 搜索、字段读取、定向取证 |
| discriminate | 区分仍存在的竞争解释 | 现有假设账本、候选选择和已授权实验 |
| synthesize | 把证据变成逐问题答案与缺口 | 问题账本、关键原文、结构化主张 |
| publish | 发布准确且有边界的结果 | 报告校验与有限修正 |

工具目录根据原始问题、当前有效补充、证据类型和阶段生成，不再仅匹配原始 objective 的关键词。

完整平台 Schema 不改写；只控制本轮展示哪些授权工具。另保留轻量工具搜索，相关工具暂未展示时可明确找到。内部执行仍校验当前权限和参数，展示变化不扩大授权。

报告工具仍允许证据足够时尽早结束，不为了阶段完整强制多调用一次模型。按需加载大 Schema 的方案需要实测，不能以“菜单更小”推断质量一定更高。

## 9. Harness 优化三：让模型直接取得问题相关证据

### 9.1 增加可读的证据地图

对已保存证据产生小型 EvidenceMap：

- 来源、原始 Artifact/哈希与采集时间；
- 内容类型、总大小；
- JSON 顶层结构及有界字段路径，或日志时间/级别线索；
- 原始材料自身声明的分页游标；
- 已读取范围、搜索范围、未覆盖部分；
- 已有派生分析及输入来源。

地图帮助找内容，不代替原文，也不是已经验证的事实摘要。大型对象的地图同样有大小和计算上限。

### 9.2 JSON Pointer 读取与运算

AssertionVerifier 已能核验 JSON 字段和统计关系。第二批在 agent_read_context 增加 pointer，复用现有 Pointer 和重复键校验，提供原文字段片段与对象/数组直接子项目录；统计仍由现有断言核验器承担。读取方式、上限及验证见第二批实施记录。

返回包含 evidence_id、pointer、源哈希、字段值/有界结果、来源与覆盖范围。解析后的 JSON 不伪装成原文连续引文。需要原文引用时返回真实片段及可验证位置；没有该位置时继续通过原文读取获取。

不预设任何游戏字段或阈值，不自动把名字包含 latency 的字段解释成帧耗时。数组截取与本地文件读取完成，不等于远端分页完成。

### 9.3 确定性分析优先

已有 crash、frame_time、CSV、日志配方继续复用。能用字段或注册配方处理时，不让模型手算大数组或先写代码。

需要通用代码时仍用现有沙箱、输入清单和派生证据链，不能因接入 Super-agent 而改成宿主机直接执行。

## 10. Harness 优化四：工作记忆与报告封套分别构建

当前已有 6,000 字节笔记上限及反证优先级，保留这套保护，增加按 question_id 定位与原文回读。

建议上下文分四层：

1. 固定任务简报、输入版本、权限与剩余预算；
2. 当前未决问题、已知答案、反证和覆盖缺口；
3. 当前动作相关的证据片段与工具结果；
4. 可检索的历史明细、过往工具输出和规划参考。

预算按字节/Token 可追踪，来源和统计口径不静默删除。大段知识包与重复工具结果优先从模型消息移出。

### 10.1 单独构造报告上下文

报告请求不再复制前三条大消息后依赖 fit_native_context 删除工具历史，而是从权威简报、问题账本、有限关键摘录和覆盖缺口重新构建。

报告封套中：

- 全部问题至少保留身份和状态；
- 有效约束必须保留；
- 引用用小片段、原文位置或已验证结构化主张；
- 不再包含完整工具目录、大量 Provider 返回预览或全部追问正文；
- 超限时明确哪些证据细节未纳入，不能静默丢掉决定性反证。

“预留报告预算”与“确认报告上下文实际装得下”分别检查。无法组装时返回具体原因，而非再让模型继续取证。

复杂问题很多时可分批形成有来源的 finding_drafts，最后由程序合并已验证条目，不反复压缩上一份自然语言总结。发布时重新校验输入版本、来源和报告状态。

## 11. Harness 优化五：推进与收尾围绕问题

当前 register_progress 已区分账本变化与有限新字节推进，继续复用。改进方向是让账本变化更贴近问题完成：

- 新证据回答了哪项问题；
- 哪项假设被支持或受到反证；
- 哪个缺口已关闭或证明无法取得；
- 相同读取/分析是否只是重复结果；
- 还有哪个合法、可负担的动作有望改变答案。

不要把计划文字改写、日志时间戳变化或不断翻页当成持续进展，也不要只因未及时点击式更新计划就判定没有进展。

报告按问题给答案：
“已证实的观察 / 尚不能证明的解释 / 缺少什么 / 下一项可执行验证”。

不能为了有个看起来完整的报告，将所有问题都标记 answered。有效但有限的报告可以结束，执行失败也必须如实失败。

外部 Watchdog 观察权威进展版本、在途操作和模型/工具心跳。执行本身卡住时才走有界恢复；合法的长任务等待不按短时间无账本变化直接判成停滞。

## 12. 把现有执行器接成 WorkerStep

当前原生路径已有 `run(max_model_turns=1)`，Temporal 每轮复用它；Local 当前一般连续运行整个调查。先提取一轮执行的边界，不重写整套控制器。

拟议返回契约：

~~~text
WorkerStepResult
  investigation_id
  outcome: continue | waiting_operation | waiting_input
           | completed | failed | canceled
  checkpoint_ref
  input_revision / progress_revision
  pending_operation_ids
  wake_sources / wake_deadline
  stop_reason
~~~

这是拟议接口，当前尚未实现。native 和 typed 各保留协议适配，通过相同结果契约交给调度层。

长模型调用仍是本轮的一部分；长平台操作或分析作业可提交后返回等待，等待期间释放计算槽位。释放计算槽位不释放设备排他租约或取消清理责任。

未完成的 assistant/tool 调用组先写执行日志，等到每个 call_id 的结果持久化后才交给下一次模型请求，不能为了让出执行而发送不闭合的工具协议。

Temporal 保留现有版本 marker 和旧工作流回放；Local 逐步采用同一轮次结果。任何调查仍只能有一个推理所有者，不能 Local 和 Temporal 同时驱动。

## 13. 轻量协调层怎样落到现有项目

### 13.1 Intake 与规则优先路由

复用 EventIngress、API 鉴权、事件载荷哈希与 incident_key。

- 指定调查 ID 的输入直接送达。
- 已绑定 run/operation 的反馈直接回到原调查。
- 已关联 incident_key 的异常补充原调查。
- 明确的新任务创建新调查。
- 缺少必要关联时保存待处理状态，再做有界判断，不把所有模糊事件都变成新任务。

首版不必引入 Router 模型。已有领域自动选择继续运行，不让用户承担日常任务分配。

### 13.2 只增加必要关联

优先新增两类记录：

- conversation_task_links：同一会话下多个独立调查；
- task_subscriptions：任务订阅的明确运行、operation 或外部线程。

均包含 tenant/project、稳定外部身份与去重约束。源事件只唤醒有关系的任务，不全局广播全部日志。

现有 conversation lineage 保留，用于续查；独立任务使用新关联，不能把不同任务都伪装成同一调查的 supersedes 子节点。

### 13.3 去重与副作用

继续使用已有 Inbox/Outbox，不引入上游 Effects 的第二套数据库。借鉴其 generation 处理，确保投递中发生新更新时，旧完成回执不能删除新请求。

任务运行结果不能因为又进入事件流而自动生成同类任务。保留 root_event_id、causation_id，区分用户请求、平台反馈和 Agent 自身输出；订阅消息只提供上下文，不增加权限。

### 13.4 统一交互

工作台提供“某任务状态”“继续指定任务”“暂停/取消任务”及任务列表。运行日志留在调查详情，前台只聚合结果、失败与真实待决定事项。

用户停止的调查不因新证据自动恢复。完成、证据不足、工具失败和待清理分别展示。

## 15. 实施顺序与可交付结果

### P0：先修三个已复现的缺口

1. 当前有效要求有来源保留，较早输入可回读。
2. 报告上下文独立构建，覆盖长追问边界。
3. 工具展示跟随有效补充和当前证据。
4. 保留现有原生流程、预算和判断规则回归。
5. 以有来源的短表示和可读取引用保留超预算内容，不将修复变成无限增长的消息。

交付：不改变运行时和平台接口的 Harness 改进；有对应反例和恢复测试。此阶段可独立发布，不等待 Super-agent 协调层。

### P1：提高一题调查的完成质量

1. 简单任务不强迫生成复杂计划。
2. 增加 EvidenceMap 和有界字段读取。
3. 加入逐问题答案、反证和缺口状态。
4. 调整阶段工具菜单并测量实际开销。
5. 用同一组保存证据比较问题回答、引用与总成本。
6. 实现单 Worker 的 Inline/Spill、历史资源发现/读取和压缩后召回测试。

交付：更容易使用现有确定性能力的调查 Worker。没有质量改善时，先回看取证策略和模型配置，不进入大规模并发扩展。

### P2：将已有轮次能力提炼成 WorkerStep

第四批接入共用 run_step、ContinuationPacket、Local 轮次排队和权限等待恢复；第五批将原生代码作业拆为提交/轮询/收集，保留实际分析名额并补清理义务。通用 MCP 长操作及完整执行器拆分仍待实施；第十七批已接入 Local/Temporal 入口执行独占与后端绑定，真实故障联调仍待完成，没有提高并发规模。

1. 明确继续、等待、完成与失败。
2. Local 和 Temporal 复用相同控制语义。
3. 长操作等待期间让出计算槽位。
4. 检查中断、旧输入、调用组闭合和预算重放。
5. 从权威账本构建 ContinuationPacket，分别恢复执行位置与当前模型上下文。

交付：可被协调层管理的现有调查执行器，不更换 Agent SDK 或模型供应商。

### P3：补轻量协调与长期运行

1. 显式会话—任务映射和订阅。
2. 已有任务反馈直达，不重复模型路由。
3. 外部健康/进展监督与按需通知。
4. 多任务、取消、重启与清理验收。
5. Router 只加载任务卡和事件批次；跨任务原文按授权引用链读取，不广播完整 Worker 上下文。

交付：持续在线的 Python Super-agent。GitHub 可以随后作为新事件源接入，不绑在核心改造关键路径。

不再给出之前完整 DSH 迁移的 15–25 天工期；本方案范围不同。先完成并测量 P0/P1，再据实际模块变化评估 P2/P3，避免用不可靠的总工期掩盖依赖。

## 16. 验证方式与实际收益门槛

### 16.1 不把协议测试当作能力评测

本轮探针只复现上下文和工具边界。后续回归覆盖：

- 第五条及更多补充不使有效约束不可恢复；
- 四条长输入仍可组装合法有限报告；
- 用户转向性能/崩溃问题后相关工具可发现；
- 早期约束冲突能说明来源，不自动猜测；
- 关键反证与未覆盖范围在报告中保留；
- JSON Pointer 结果不伪装原文，引文与主张继续独立核验；
- Worker 让出/恢复不重复运行或重置预算；
- 新消息到达使旧动作/报告失效；
- 租户、构建、环境和统计口径不混淆。
- 关键早期信息被移出窗口后仍可沿引用找回，且跨任务上下文不串扰；
- 事件批处理保留失败/恢复和原始事件索引，取消不被普通批次阻塞；
- 新窗口能恢复目标、反证、在途操作和剩余预算，不重复已完成副作用。

### 16.2 三层评测

1. **确定性反例**：输入、上下文、工具菜单、来源/预算/报告门禁。
2. **固定证据调查**：同题、同模型、同参数、同预算比较改造前后。
3. **已授权真实实验**：只在需要验证环境执行时运行，不为证明协调架构而反复启动游戏。

使用不同题型和字段结构，覆盖性能、恢复、崩溃、基础设施、证据不足与冲突来源。不能只调优当前这一题的断言名或运行 ID。

### 16.3 衡量“更实用”

| 指标 | 衡量对象 |
| --- | --- |
| 问题回答率 | 用户问题中被证据实际回答的比例 |
| 错误结论/过度推断 | 指标偷换、范围扩大、错误因果或恢复结论 |
| 无效读取比例 | 重复或未推进问题的取证 |
| 有效有限报告率 | 预算停止前是否能清楚交付已知与未知 |
| 实际模型成本与耗时 | 包括候选、规划、监督和重试 |
| 交互恢复能力 | 追问、纠正、取消、重启是否连续 |
| 资源正确性 | 重复执行、环境冲突、未完成清理 |
| 人工介入 | 是否只在真正缺输入、权限或决定时需要用户 |

硬性一致性检查要求零违反。模型质量和成本目标在固定基线后登记；不预先承诺提升百分比。
